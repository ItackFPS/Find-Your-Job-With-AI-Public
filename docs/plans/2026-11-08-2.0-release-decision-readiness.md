## 1. Executive summary

1. **The daily database question is answered, with one uncomfortable detail.** The database is not
   configurable: it is `<folder holding the code>/data/jobs.db`. On this machine the only registered
   application (Start Menu, uninstall entry) writes to
   `%LOCALAPPDATA%\Programs\Find Your Job With AI V1\data\jobs.db`. That is the authoritative
   production database. But **no database is in daily use.** The installed database holds only
   install-day data. The real history sits in a private development checkout, which is not an
   installed application.
2. **A release blocker the audit missed: upgrading from v1 leaves v1 configuration in place.** The
   installer writes `config/*.yaml` only when missing. After an in-place upgrade, v2 code would run
   on v1 `schedules.yaml` (no `pipeline_daily`, so no background search) and v1 `sources.yaml` (no
   `france-travail-web`, and removed sources reported on every run). The existing upgrade test cannot
   see this because it upgrades a version to itself.
3. **Releasing before L6–L8 is architecturally safe**, provided a new ADR records it. No invariant,
   and no release gate except one, depends on those layers.
4. **The audit's proposed replacement for the multi-occupation gate is rejected here.** "No occupation
   logic in production" is true by construction and protects nothing. A real temporary gate is
   defined in §4 D2. The concern is not theoretical: the France Travail web collector only reads
   IT occupations, so a non-IT user gets no France Travail offers.
5. **Three audit items change.** France Travail credentials should not block 2.0 because the API is
   closed to new users (External). Autostart already has a no-terminal path in the tray menu. Removing
   the Profile page's v1 editors is unsafe as written because the hard filter still reads those fields.
6. **Recommended scope:** deterministic matching only, AI controls hidden (backend kept), no France
   Travail credential field, a small Today card instead of the three-lane Home, and an explicit
   statement that 2.0 is tuned for IT and digital roles.
7. **Nothing on the release path depends on L3 activation.** L3 and L4 stay SHADOW, activation stays
   off, L5 stays inert, deterministic eligibility and ranking stay authoritative.
8. **Shortest safe route:** M0 records → M1 upgrade safety → M2 scope cuts and safety gate → M3 setup
   without a terminal → M4 UX → M5 qualification and release. The owner's human checks run alongside.

## 3. D8: database investigation

### 3.1 How the path is determined (Code)

- `src/api/app.py:422-427`: `_PROJECT_ROOT = Path(__file__).resolve().parent.parent.parent`, then
  `_DB_PATH = _PROJECT_ROOT / "data" / "jobs.db"`. The runner, scheduler, staging stores and privacy
  flows all receive this value through `app.state.db_path`.
- **There is no override.** No environment variable, `.env` key or YAML setting changes it.
  `grep` finds no `DATABASE_URL` use in `src/` and no `environ` lookup in `src/storage`, the runner or
  the scheduler. `.env` affects ports, the LLM endpoint and credentials, not the database.
- It does not depend on the working directory for the main application. The database follows the
  code: **each copy of the application has its own database.**
- Connections set `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`
  (`src/storage/sqlite.py:85-89`). The file header confirms WAL on the three main databases.
- Migrations run from `init_db` at every start: additive columns, then one-shot data migrations
  recorded in `db_migrations` (`src/storage/migrations.py`).

### 3.2 Startup paths

| Start method | Database | Note |
|---|---|---|
| Start Menu or desktop shortcut, 1.0 (`FindYourJob.cmd`) and 2.0 (`pythonw -m src.launcher tray`) | `<install>\data\jobs.db` | `.iss:90,96`, `WorkingDir: {app}` |
| Autostart (`tray --window none`) | same | `autostart.py`, from the install root |
| `FindYourJob.cmd` in a checkout or worktree | that checkout's `data/jobs.db` | `cd /d "%~dp0"`, launcher `os.chdir(root)` (`__main__.py:69`) |
| `scripts/Start_backend.bat` | its checkout's `data/jobs.db` | `cd /d` to the project root. No scheduled task uses it today |
| `uvicorn` from any directory | `data/jobs.db` beside the code | but see below |
| CLI (`src.main`, `src.evaluation`, `src.lab`, `src.feedback.cli`, `src.storage.migrate`, `src.personalization.cli`) | **relative** default `data/jobs.db` | depends on the working directory |
| `/api/esco/*` | **relative** `data/esco.db` (`routes/esco.py:33`) | correct only because the launcher changes directory |
| Docker | `/app/data/jobs.db` in the container | `DATABASE_URL` and the `/data` volume in `docker-compose.yml` are **ignored**, so container data is not persisted. Not a 2.0 Windows path |

**Can another startup select a different database?** Yes: starting any other copy of the code. There
is no fallback and no silent redirection, but nothing tells the user which copy is running. A CLI
tool started in the wrong directory would address a different relative path.

### 3.4 Answers

1. **Actual daily database.** By configuration, the V1 install's `data\jobs.db`. By observed use, no
   database is in daily use: V1 received no new offers after install day, and the private database
   is no longer run.
2. **What determines the location.** The location of `src/api/app.py` on disk. For an install, the
   folder chosen at install time; Inno Setup reuses it on upgrade through the fixed AppId.
3. **Launcher.** The Start Menu shortcut. In 1.0 it runs `FindYourJob.cmd`; 2.0 replaces it with the tray.
4. **Accidental selection.** Yes, by double-clicking `FindYourJob.cmd` in another copy, including the
   orphan preview folder or a worktree. This is a developer-machine risk, not an end-user one.
5. **Protection from laboratory and test operations.** Good.
   Lab: separate `data/lab.db` and `data/lab/`; a write guard refuses any writable root that is,
   contains or sits inside the database and its side files, `config`, `src`, `.git`
   (`src/lab/guard.py:262-285`); production never imports `src.evaluation`
   (`tests/test_evaluation_isolation.py`).
   Tests: autouse fixtures fail any test that writes to the real `data/` or `config/`
   (`tests/conftest.py:98,141`). Self-check opens the database read-only.
   Residual: the guard protects `<root>/data/jobs.db` plus an explicit `--jobs-db`, and relative CLI
   defaults depend on the directory.
6. **Installation, migration and upgrade risks.** See §3.5.

**What cannot be established from evidence:** only the owner's intent, namely whether the private
history should ever be carried into the installed application.

## 4. Decision analysis, D1–D8

### D1: Release before L6–L8

**Situation.** ADR 0027 orders L1→L8, then P3, P5, P6, P7. It lists one dependency for P3: the occupation
picker lands with L6 and is reused by the wizard. Activation is never a stage exit criterion.

| L6–L8 capability | Needed for usable 2.0? | Why |
|---|---|---|
| L6 ROME pack, classifier, `job_occupations` | No | Keyword domain path is today's production behaviour and the pack's documented fallback |
| L6 occupation picker | No | `target_domains` picker exists; the wizard must leave room for a later step |
| L6 transferable skills, "Reconversion" lane | No | Advanced |
| L7 market plane | No | No criterion in completion plan §P.5 uses it |
| `matches_salary` correction | No | Latent: no shipped profile or UI field sets salary requirements |
| L8 full self-monitoring | No | Its missing metrics monitor L6, which will not exist. L2 source and field detectors ship |
| **Non-IT coverage** | **Partly** | L6 was the planned answer. See D2 |

**Release gates assuming these layers.** Only the multi-occupation self-check. The others test what exists.

**Options.**

| Option | For | Against |
|---|---|---|
| A. Keep ADR 0027 order | No governance change | L6 is itself gated on unread licence terms and a corpus; delays a usable product for capabilities no criterion needs |
| B. Release first, recorded in a new ADR (**recommended**) | Shortest route; preserves all invariants | L6 work later touches a released product and profile contract |
| C. Release first, no record | None | Silently invalidates an accepted ADR |

**Hidden debt under B, to record.** A later `targets.occupations` and salary contract means another
profile version bump (the migration path exists). ADR 0026's "Reconversion" section cannot be complete
before L6. ADR 0023's preconditions remain open. The evaluation corpus for L6 is not built.

**Requires approval.** New ADR 0028 stating: 2.0 ships after P3, minimum P6 and P7; L6–L8 move to 2.x;
ADR 0027's order and its multi-occupation gate are superseded only for 2.0; every other ADR 0027 gate
stays. ADRs are not edited.

### D2: Multi-occupation self-check

**Purpose.** ADR 0023: it "guards every occupation, not just IT": 6 profiles (nurse, accountant, warehouse
operative, sales representative, systems administrator, chef), 600 offers, ≥ 80 % of each top 20 target or
related occupations, 0 strong-rule regressions (proposal §AD-7). The 80 % target is an L6 exit criterion
measuring classifier quality. The guarantee behind it, that the app is not silently IT-only, applies today.

**Existing coverage.** `test_hard_filter_profile_adaptability.py` (24 tests) and
`test_profile_driven_filter.py` (57) prove the engine has no occupation branch and follows the profile.
`test_off_domain_vocabulary_coverage.py` covers vocabulary. The synthetic self-check has one dataset.
**None runs a non-IT profile end to end against a recorded baseline.**

**Actual exposure (Code).** The France Travail web collector keeps only domains in `OCCUPATIONS`, which are
all IT (`france_travail_web.py:68,179`). The France Travail API is closed to new users. So a nurse on a fresh
install gets no France Travail offers and depends on EURES, remote boards and opted-in unofficial sources.
Whether off-domain vocabulary such as `non_it_title_functions` wrongly penalises non-IT targets is
**untested** and is what the gate would discover.

**Options.**

| Option | Assessment |
|---|---|
| Audit: "no occupation logic in production" | Rejected: cannot fail, weakens the gate |
| Waive until L6 | Honest but leaves a known gap unmeasured |
| Require the full L6 gate | Blocks 2.0 on L6 |
| Temporary deterministic gate plus honest scope (**recommended**) | Measures the real risk, claims nothing about L6 |

**Recommended temporary criterion, G-MO-T** (does not claim L6 is complete):

1. Same six ADR 0023 profiles, as committed fixtures, with a fixture corpus designed to grow into the 600.
2. **Blocking:** 0 strong-rule regressions against a recorded baseline, and 0 clear-target offers rejected
   by a domain or off-domain rule, per profile.
3. **Reported, not gated:** top-20 target share per profile, labelled "deterministic baseline, not the
   ADR 0023 criterion". No threshold is set before a baseline exists (ADR 0023's own rule).
4. **Yield statement per profile:** which sources return offers with no credentials and no opt-in.
5. The original gate stays open and re-enters with L6.

A failure means fix the vocabulary or narrow the stated 2.0 scope. It is never a threshold change.

### D3: AI scope

**Situation.** `/api/ai/*` covers runtimes, hardware, catalogue, Ollama install, pull and benchmark. No
frontend calls it. The Dashboard switch (`Dashboard.tsx:558`) sends `use_ai` without any setup check.
Without a server, Phase 2 fails soft and the run continues (`orchestrator.py:1213`), so the switch
misleads rather than breaks. `llm_eligibility_enabled` is not exposed in the Profile page.

**AI is not required** for collection, eligibility or ranking. Semantic embeddings are separate and
fail open to the deterministic ranking (`orchestrator.py:1279`, `test_semantic_stage_fail_open.py`).

| | Path A: full AI in 2.0 | Path B: hide, 2.1 (**recommended**) |
|---|---|---|
| Work | Runtime and model steps shared by wizard and Settings; persisted model choice (today env-based, a config contract change); pull and benchmark progress; memory and failure states; gated run option; EN/FR; hardware validation on 2–3 machines. §P.5 "AI grounding ≥ 95 % quotes" needs F8.4, which does not exist | Remove the Dashboard switch and its strings; a guard test; docs. One small PR |
| User-facing value at release | Optional enrichment only | None lost that works reliably today |
| Risk | Largest uncertainty on the release path | Low |
| Preserved | Everything | **All backend work, API, `use_ai` parameter, run history badge** |

**Requires approval.** Path B amends §P.5 "AI optional" (UI setup part) and "AI grounding", and R-C3 for
2.0. It is not abandonment: P3.2 and P5 become the 2.1 headline.

### D4: France Travail credentials

- **External (opened today):** the data.gouv.fr listing states the API "n'est actuellement plus exposée".
  It describes this as temporary, marks access restricted, and offers a contact form. No date is shown.
- **Code:** only the France Travail API source needs credentials (`france_travail.py:145-151,202`); without
  them it is skipped with a reason (`orchestrator.py:460`). Everything else runs. A release without them
  is useful, subject to the IT-only limit in D2.
- **Existing mechanism:** `.env` through `load_dotenv` (`app.py:40`), or `client_id` keys in source config.
  No keyring or DPAPI. `python-dotenv` is packaged.
- **If a field were added:** the secret stays in `.env` in the user profile; the API must be write-only and
  return only "configured"; never logged. `delete_all` lists `*.local.yaml` but **not `.env`**
  (`delete_all.py:198`), so Delete All would need extending. The lab isolation report already flags `.env`.

| Option | Assessment |
|---|---|
| Blocker, as the audit said | Builds a field almost no new user can fill |
| Defer, remove the `.env` instruction (**recommended**) | Removes the no-terminal violation for the mainstream journey |
| Remove the source | Loses function for existing key holders |

**Recommended for 2.0:** remove `.env` steps from the first-run guide; show the API in Sources as
"not required, restricted access" with a friendly reason instead of the raw variable names; keep `.env`
support documented as advanced. Field deferred until France Travail reopens access or demand appears.
Reports and logs never show credential values.

**Requires approval:** this reads R-C5 as not covering a source new users cannot subscribe to.

## 12. Release acceptance checklist

Each line is reported met or **not met** in the §H report. **[A]** automated, **[H]** human, **[A+H]** both.

**Clean install and first launch**
- [ ] [A+H] Installer completes without admin on clean Windows 10 or 11; exit code 0.
- [ ] [H] Window appears without a terminal; ≤ 3 s first window; backend ≤ 10 s warm, ≤ 25 s cold (measured).
- [ ] [A] Installer < 100 MB; installed < 400 MB (measured), or recorded as not met.

**Onboarding and profile**
- [ ] [A] Wizard completes with no file edit; resumable after close.
- [ ] [A] Profile persists across restart and upgrade; no search before first save.
- [ ] [H] 3 non-technical users: onboarding < 10 min; 3 relevant offers saved < 5 min, unaided.

**Database and upgrade**
- [ ] [A] App opens exactly `<install>\data\jobs.db`; startup log states the path.
- [ ] [A] v1.0.0 → 2.0 on the built installer: row counts of `jobs`, `feedback_events`, `outcome_events` unchanged.
- [ ] [A] Backup exists before migrations regardless of size; `PRAGMA integrity_check` = ok after.
- [ ] [A] Unedited v1 config refreshed; edited config preserved; `pipeline_daily` and `france-travail-web` active.
- [ ] [A+H] Rehearsal on a large database copy and on a copy of the real V1 folder.
- [ ] [A] Interrupted migration resumes; two starts idempotent.
- [ ] [H] Documented manual restore performed once.

**Collection and sources**
- [ ] [A] A failing source never fails the run; a changed page raises a canary error, never silent zero.
- [ ] [A] Dedup one offer with several provenances; expiry only on complete listings.
- [ ] [H] One live FT web + EURES duplicate observed (or not met).
- [ ] [A+H] Fresh install, no credentials, unofficial off, IT profile → FT web offers present.
- [ ] [A] Yield per G-MO-T profile stated.
- [ ] [A] Unofficial sources off by default, explained, recorded, revocable.

**Eligibility and ranking**
- [ ] [A] Self-check: 0 unsafe rejections; baseline identical.
- [ ] [A] G-MO-T blocking parts green; original gate recorded as deferred to L6.
- [ ] [A] Held-out precision@Strong and recall@20 with CIs, "insufficient evidence" stated; no promoted change.
- [ ] [A] `activation_enabled` and `experimental_enabled` false, every `weak_evidence_mode` = `reject`, on fresh and upgraded installs.
- [ ] [A] Fault-injection pause, INV-2 socket test, reset bit-identity, erasure verification, lane caps.

**Models**
- [ ] [A] Download shows size and progress; verifies the pinned revision and integrity; retry works.
- [ ] [A] Offline: clear message, deterministic results still produced.

**Background and recovery**
- [ ] [H] 24 h window closed: one daily run recorded. Reboot resumes with autostart on. Disable works.
- [ ] [A+H] Quit leaves no process. Port taken, disk full, offline each give a clear message.

**AI**
- [ ] [A] No UI path enables AI; `/api/ai/*` still present; full journey without an LLM.

**Accessibility and language**
- [ ] [A] axe-core 0 serious. [H] Keyboard-only wizard and apply journey; AA contrast.
- [ ] [A] EN and FR 0 missing keys; pseudo-locale clean.

**Quality gates and docs**
- [ ] [A] Full backend, frontend, lint, audits, gitleaks and installer acceptance green on the release build.
- [ ] [A] Host/Origin/loopback/traversal probes, instance token, no outbound profile data.
- [ ] [A] No Discord, n8n or digest code or settings.
- [ ] [H] README, installer and app guides describe 2.0, with stated limits.
- [ ] [H] Owner approval to release and tag.

**Cannot be proven by automation alone:** usability; real 24 h behaviour on a user session; real hardware and
WebView2 variation; live source behaviour; upgrade from a genuinely used install; contrast judgement.

## 13. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Config migration overwrites a user edit | Lost settings | Hash-gated replace, backup, tests with edited fixtures |
| Upgrade tested only on small databases | Data loss | Mandatory large-copy rehearsal |
| Profile v2 editor removal changes filtering | False rejections | Equivalence test before removal |
| G-MO-T reveals systematic non-IT rejection | Scope or work grows | Fix vocabulary or narrow claim; no threshold change |
| Non-IT users see few offers | Poor first impression | Stated limit; optional `OCCUPATIONS` extension |
| France Travail page structure changes | Yield drop | Canary, breaker, sitemap-driven pages |
| France Travail reopens API | Field wanted | Small follow-up |
| Usability findings arrive late | Delay | First build to testers right after M3 |
| Installer exceeds size target | Criterion not met | Measure early in M5; slim manifest only then |
| Reports committed separately | Invalid test taken as guidance | One PR, correction prevails |
| Public exposure of machine facts | Privacy | Owner reviews §3.3 |
| ADR 0028 misread as permission to activate L3 | Safety | ADR states activation is unaffected |
